## Current decision

- The existing Owner Console Auth project remains a separate concern; do not route POS transaction writes to it.

- No database schema, production secrets, environment variables, or deployment settings were changed by this repository update.

## Repository changes in this transition

- Remove the hard-coded Supabase pooler region from the production database-target classifier in source and the checked-in server bundle.
- Add regression coverage showing the classifier is region-agnostic while still not treating arbitrary database hosts as Supabase poolers.
- Document `PRODX_DB_BROKER_URL` in `.env.example` without supplying a real endpoint or credential.
- Keep production database resolution fail-closed through the authenticated broker. Do not add a default project URL, direct-connection fallback, or cross-project fallback.

## Required before a new target can be approved

1. Owner selects the Supabase organization for the replacement project.
2. Create the new POS transaction project in the approved region and record its project reference.
3. Inspect its schema, migrations, RLS, grants, backup/recovery configuration, and migration-head consistency.
4. Reconcile the repository migrations against that exact project using a safe preview/test database first.
5. Provision a least-privilege runtime database role and authenticated broker; verify OIDC issuer, audience, expiry/signature, and exact production subject allow-list.
6. Configure the broker endpoint only after verification; never put database credentials in frontend variables or commit them.
7. Run migration, PostgreSQL integration, tenant/store isolation, financial/inventory integrity, idempotency, lint, typecheck, build, architecture/security gates, and required CI on the exact commit.
8. Verify live `/api/v1/healthz`, `/api/v1/readyz`, and retained production smoke evidence before considering release.
